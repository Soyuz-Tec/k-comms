# Identity operator recovery runbook

This runbook covers the IdentityAccess controls introduced by ADR-0090. No
provider is selected or enabled by the default configuration. Use synthetic
accounts in development and staging.

## Configuration and custody

OIDC must have an exact HTTPS issuer, registered client ID and independently
held client secret, exact reviewed HTTPS callback URI and allowed redirect list,
and reviewed required assurance values. The configured issuer must support code
flow, S256 PKCE and RS256 signing. Discovery/token/JWKS redirects are refused.
Do not enable federation to satisfy a declaration without a successful approved
provider sandbox journey. SCIM subject mapping is an additional reviewed setting
and defaults off; it must map a stable provider subject for a newly provisioned
identity and never a mutable email.

Identity encryption uses `identity_secret_encryption_key` or its keyring with an
active key ID. Hold those keys separately from webhook and push keys. Missing or
unavailable keys fail enrollment and federation closed. During rotation retain
old keys until every pending challenge has expired and all live MFA factors have
been migrated through an independently reviewed key rotation procedure. Do not
remove a retained key merely because the active key ID changed.

SCIM credentials are generated by the existing privileged Service Accounts
workflow after recent verification, with `scim:read` and/or `scim:write` scopes.
Save the one-time credential in the provider secret store. Use one credential
per tenant and provider. Rotation immediately invalidates the old generation;
revocation and expiry stop further resource reads and writes. Users and Groups
are tenant scoped. Group membership grants no tenant or platform roles.

## Account factor recovery

A user should first use an unused recovery code on the MFA challenge. A successful
code cannot be replayed. Account password reset retains the MFA requirement.
Replacing recovery codes or disabling a factor requires recent password/factor
step-up and a different recovery credential or the next authenticator time
step. Other sessions are revoked. Recovery credentials display once and must
never enter support tickets, screenshots, audit metadata or application logs.
Five bad attempts lock a factor for five minutes; login challenges separately
expire after five minutes and five attempts. Start a new login after expiry.

If the user has lost both authenticator and recovery credentials, do not clear
MFA rows manually or use SCIM/invitations to reset the factor. Stop and use the
organization's reviewed independent identity recovery procedure and security
review. No unauthenticated MFA-reset API is provided.

## Provider outage and emergency owner path

Keep one existing owner account's local password and, when enrolled, an unused
factor/recovery credential outside the IdP dependency. The independent
`identity_break_glass_secret` must be absent unless an approved recovery custody
plan exists. Two custodians should independently hold the owner credential and
operator recovery credential. Do not paste either into a tracked file or shell
command history.

An authorized operator may invoke the owner-internal
`Accounts.break_glass_session/1` from the controlled application console with
the separately held `credential_token`, existing `tenant_slug`, `email`, current
`password`, enrolled `mfa_code`, operator `actor` and specific `reason`. No HTTP
route invokes this operation. It creates an existing owner session with a fixed
fifteen-minute absolute expiry; it does not grant a role or remove a factor.
Arrange secure session handoff without printing credentials into retained logs.

Immediately verify `identity.break_glass_used`, operator/reason attribution,
the fifteen-minute deadline, and delivery of the configured operator audit alert.
Missing alert delivery fails the recovery drill. Perform the necessary recovery,
revoke the emergency session through the existing session command, rotate the
operator credential, reconcile the tenant's active owners and record a redacted
incident receipt. Never use the emergency path for routine administration.

## Suspension and qualification drill

Provision an ordinary synthetic member with a SCIM credential. Authenticate its
linked corporate subject, open a socket and join an allowed call. Suspend it via
SCIM with the current ETag. Verify that refresh, access lookup, socket commands,
push authorization and call credentials all fail; record elapsed latency and
socket disconnection. A stale ETag, foreign tenant ID, privileged role input or
attempt to suspend the last owner must fail without a partial mutation. Rotate
and revoke the SCIM credential and verify the old credential stops immediately.

Run the independent owner recovery drill, MFA one-use/rate-lock drill and a DND
schedule across an overnight/DST boundary. DND must defer actual outbound
email/push and incoming ringing, retain the inbox, and permit voluntary joining.
Retain exact-candidate sandbox receipts, independent alert/custody proof,
backup/restore and rollback evidence before protected production promotion.

## Rollback and privacy

Keep the expanded schema when rolling the application image back. Once enrolled
factors or SCIM scopes exist, an older application that ignores those controls
is not an acceptable identity rollback. Maintain enforcement or use the reviewed
recovery plan. The target must declare `enterprise_identity_v1` or pass the
current release's quiesced zero-hazard owner projections. Retained pending
enrollment, federation/SCIM tombstones, SCIM service scopes and enhanced-auth
sessions count independently of ordinary user status. A live sliding session
deadline still counts after its absolute deadline because an older runtime
could ignore that bound. Preserve the approved target's actual immutable
capability declaration. Never drop factors, federation links or directory tombstones to
force a release. The restored old service-scope constraint intentionally refuses
retained SCIM credentials during a down migration.

Ordinary SCIM deletion suspends an identity and retains its immutable key to
prevent identity reuse. The separate governed erasure workflow removes the
IdentityAccess personal rows, avatar and availability while retaining required
minimal audit evidence under the tenant's governance policy.
