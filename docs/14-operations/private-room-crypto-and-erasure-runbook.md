# Private-room crypto and pending erasure

Provider creation flags default OFF. This runbook documents proof prerequisites; it grants no activation or security acceptance.

Configure one explicit HTTPS Matrix homeserver origin and its independent canonical server_name. Supply identity-admin and device-less room-control authentication only through protected deployment environment/secrets. Retain provider configuration and auth-secret AEAD keyring for cleanup even when `MATRIX_CLIENT_PROVISIONING_ENABLED` and `PRIVATE_ROOMS_ENABLED` are false. Encryption/recovery keys and local store passwords never belong in server configuration. Configure native Synapse refreshable access-token lifetime at no more than 180 seconds; longer/missing/invalid leases fail provisioning and preserve a stable-device cleanup obligation. Standard native `whoami` must confirm exact participant user/device. Control `whoami` must have no device; native device inventory and all public signing key inventories must be empty.

Enrollment returns a short client authentication credential to the exact active K session. Device/session withdrawal schedules native deletion of the entire stable Matrix device, not merely one known token; the reconciler requires native absence. Reconciliation runs each minute. Raw native authentication can survive K withdrawal until successful native revocation or its maximum 180-second lease. Application UI, opaque sends and replay require current retained K authority; this limitation must be evaluated during provider security qualification rather than described as immediate native token invalidation.

Participants save their maintained SDK recovery key or verify a second device using matching SAS. The local password encrypts the IndexedDB crypto store; it is not server recoverable. Existing identities are never automatically reset. Locking clears memory/plaintext; forgetting clears the current Matrix device's entire browser crypto store. A successful browser action covers only that actual store. It cannot prove deletion of earlier browser profiles, offline devices, another recipient's store or independent copies. Browser tracing/video is disabled in the private protocol test because recovery/authentication secrets can appear in setup.

Governed user erasure includes every private room where the user was ever a participant. Membership removal does not remove original-author lineage. The complete derived room is fenced, including other participants' ciphertext, while unrelated rooms survive. Any matching hold or unknown lineage refuses the effect. An unknown creation ACK is recovered by immutable native alias in cleanup-only mode; recovery cannot create or invite. An unknown ban ACK keeps rekey fencing. Native room purge retains the legal-hold fence through the request, persists the provider delete ID and requires actual completion with no failed participant kicks. Provider restart or expired delete-status evidence may leave cleanup pending; absence/404 alone does not create proof.

Native room purge and local ciphertext deletion are useful completed cleanup steps. They do not enumerate and purge every recipient's encrypted key-backup version or prove deletion of managed local stores. Standard Synapse APIs cannot supply the complete required receipt in this source milestone. `key_cleanup_state=unconfirmed`, provider-purged metadata and pending Governance request remain durable; operators must not mark a checkbox, patch a row, delete tombstones, reset identity, or promote a provider purge into completed erasure. There is no confirmed-bit API. A future separately installed and qualified provider module/backup enumeration protocol plus managed device-store acknowledgements must establish scope, generation, all historical recipients, every backup version, key identifier, durable receipt and hold-safe ordering before completion is possible. Independent recipient/offline copies remain a documented boundary requiring a separate product policy.

Before activation, Root qualification must run compile/format/type/lint/contracts, the actual owner authority/concurrency/erasure and disposable migration/rollback cases, and the live Matrix Rust browser journey with two fresh human principals, recovery and verified second-device flow. Also qualify adversarial provider key changes, native membership authorization/power levels, token lifetimes/revocation, tampered envelopes, unknown ACK across restart, pending sequence holes, stale generation replay, current session expiry, hold-vs-purge races, response/capacity exhaustion, and local encrypted-store failure. Federation/native mobile and encrypted calls/files are separate explicit scope. Record actual commands/exits/provider version and sanitized proof without secrets; source tests and production audit alone do not establish E2EE security.

Rollback targets must declare `private_rooms_v1` whenever any Matrix identity/session proof, private-mode conversation/room, opaque event/tombstone or active device/purge job exists. All three down migrations refuse retained rows. Preserve pending proof and source fingerprints; never clear them to make rollback pass.

The web product currently supports English. The pinned drawing engine embeds English; packaging removes only its unsupported locale import graph with an exact source hash and entry-count guard. Keep that guard and explicit host locale during dependency upgrades, and review any newly supported language before changing the transform. The maintained engine and normal all-emitted JS/CSS ceilings remain unchanged.

The encrypted-client Rust WebAssembly payload adds 7,826,886 bytes (2,092,621 gzip) beyond existing JS/CSS budgets. It loads only from the explicit private-room crypto path, is absent from the initial static entry closure, and is not installed into the service-worker offline precache. The binary contains public program code; encrypted IndexedDB, authentication credentials and recovery/message keys must never be placed in static artifacts or Cache Storage. Validate actual production `application/wasm`, same-origin immutable artifact routing, cache release behavior and first private-room download on supported browsers before activation. The local synthetic cache tests do not establish production proxy behavior.
