# ADR-0061: Store attachment derived renditions as variants

- **Status:** Accepted
- **Date:** 2026-07-29
- **Owners:** Architecture and content

## Context

Every image attachment is delivered as a full-size download. Rendering a
preview inline requires a smaller derived object, and the attachment lifecycle
has no place to record one.

Two shapes were available. Columns on `attachments` describe exactly one
rendition and require a migration on the attachment table for every additional
one. A separate table keyed by rendition kind describes any number, and the
documented data model in `docs/03-domain-and-data/database-schema.md` already
anticipated `attachment_variants`.

A rendition is generated by the client, so it is untrusted content. It is also
the only attachment surface rendered inline rather than downloaded, which makes
its content type a security property rather than a presentation detail.

## Decision

Derived renditions are rows in `attachment_variants`, owned by the
conversation-content context and keyed by `kind`. The first kind is
`thumbnail`.

A variant is constrained as untrusted inline content:

- Its content type is restricted to non-executable raster formats at the
  database, the intent validation, and the storage adapter. SVG is excluded
  because it is scriptable.
- The upload presign signs the content type, so the object store rejects an
  upload declaring anything else.
- The download presign forces that pinned type and inline disposition. This is
  a deliberate exception to the attachment disposition forced on ordinary
  downloads, and it holds only because the type is pinned at both ends.
- A variant is never served before its parent attachment is downloadable,
  because it is derived from content the scanner has not yet cleared.
- The tenant is carried on the row and pinned to the owning attachment's tenant
  by a composite foreign key.

A variant is an enhancement. Failing to authorize or verify one never fails the
attachment it belongs to.

## Consequences

Additional renditions -- a larger preview, a second size, a blurhash -- become
another kind rather than another migration on `attachments`, and deletion
covers them without a new branch because it enumerates an attachment's
variants.

Each variant is a separate object at its own key, and purging is exact-match by
key, so every deletion path must remove variants explicitly: abandonment purges
each variant key before recording the attachment clean, governed erasure
carries each variant identity to the deletion worker before deleting the rows,
and the deletion worker fails the request if a variant object survives.

The boundary manifest widens by one owned table. That widening is recorded as a
reviewed transition against this ADR.
